# Changelog

## v1.8.0

- **New: DOF adapter in Camera Assistant** (`dofadapter`, in Camera). Adds `SUPPORT_CAMERA_ASSISTANT_DOF_ADAPTER` to `camera-feature.xml`, which brings up Camera Assistant's DOF (depth-of-field) adapter option for manual-focus adapters. Rebuilt from stock at every apply; a reboot restores stock.
- **New: 8K recording while mirroring** (`mirror8k`, in Camera). Adds `SUPPORT_CAMERA_ASSISTANT_RECORDING_8K_WHEN_MIRRORING`, so the phone records 8K while mirrored to a display over HDMI or Smart View, with the matching Camera Assistant option. Rebuilt from stock at every apply; a reboot restores stock.
- **New: longer recording limits** (`longrec`, in Camera). Sets `MAX_SEAMLESS_ZOOM_RECORDING_TIME_LIMIT_IN_OVERHEAT_CONDITION` and `MIN_RECORDING_TIME_TO_ENABLE_LOW_POWER_MODE` to 3600 seconds (1 hour; stock is 300 seconds, 5 minutes), modifying the entries or inserting them when the stock file lacks them. Rebuilt from stock at every apply; a reboot restores stock.
- **Fix: 24 fps Video showed only the 1x lens** (`cam24fps`). The stock `camera-feature.xml` has `seamless-zoom-support="false"` on `BACK_CAMCORDER_RESOLUTION_FEATURE_MAP_3840X2160_24FPS` and `..._1920X1080_24FPS`, so once those entries were opened to standard Video, UHD and FHD 24 offered no 0.6x / 3x / 10x switch. The apply now sets `seamless-zoom-support="true"` on those two entries; the 8K 24 fps entry keeps `false`, so the 10x stays hidden there.

## v1.7.2

- **Fix: Chromium browsers such as Vivaldi crashing on launch with `hideksu` on** ("GPU process isn't usable. Goodbye."). Some apps run their own app zygote (`<package>_zygote`) to start their sandboxed processes. It inherits Android's zygote's open files, which include the framework resource overlays, such as the `display` tweak's `/product/overlay/s23tweaks-aodbright.apk`. On every fork, zygote code reopens those files by path. Once `hidemnt` had detached the module's mounts in the app zygote's namespace, the reopen failed (`Failed open(/product/overlay/s23tweaks-aodbright.apk)`), so the sandboxed GPU and renderer processes died before they started. In an app zygote's namespace (the zygote and the sandboxed children that share it), `hidemnt` now keeps only the mounts that hold a file the app zygote has open, which is `/product/overlay` here, and detaches every other module mount. The app's own process still sees no module mounts. Seen with Vivaldi 8.3 on an S23 Ultra: it crashed on every launch, and after the fix it opens normally.

## v1.7.1

- **Fix: `wideflash` did nothing on a camera that had been used before.** Samsung Camera reads `SUPPORT_FLASH_IN_WIDE_LENS` only as the default of its own setting, `flash_in_wide_lens` (the switch behind Camera Assistant's wide-flash option). A camera that has already been opened saves that setting as `0`, so the 0.6x lens kept the flash greyed out even with the feature switch on. The apply now turns the setting on once, after stopping the Camera and with the earlier value saved. Unpicking `wideflash` or running cleanup puts it back exactly as it was. After that first apply, a choice made in Camera Assistant is kept. Seen on an S23 Ultra (S918W) where the Camera had been used: the flash is greyed out at 0.6x on v1.7.0 and works after this fix.

## v1.6.0

- **New tweak: Dual SIM 5G** (`dual5g`, in Carrier). With two SIMs, the S23 Ultra gives 5G standalone only to the SIM set for mobile data; the other one drops to LTE, and the two swap within a second when the data SIM changes. The modem (Snapdragon X70) supports 5G on both SIMs in dual standby, and Android already asks it for 5G on both (`persist.radio.support.dualrat=2`, NR in both SIMs' allowed network types). The limit is in the modem's Qualcomm policy files: `device_config.xml` turns 5G+5G on only for the networks in `msim_plmns`, which `global_defines.xml` sets to `460-* 712-*` (China, Costa Rica); everywhere else the modem runs 5G+4G and `disable_sa_ndds.xml` removes the SA bands from the non-data SIM. `dual5g` adds the mobile country codes of the SIMs in the phone (all of a country's codes where it has several: India, the US, Japan, the UK) to `msim_plmns`. The file is in the modem's own storage (EFS). A new tool, `files/efstool` (source in `src/efstool`), reads and writes it on the phone through the stock `/vendor/bin/diag_socket_log`, which bridges the modem's DIAG interface to a local socket; no computer or flashing. Policyman reads the file when the modem starts, so a change is followed by a modem-only restart (remoteproc `mss`, about 15 s without signal, no phone reboot); later applies that find the list already complete write nothing. This is the one tweak that stays after a reboot, so it backs up first: the original file (plus `device_config.xml` and `disable_sa_ndds.xml` for reference) goes to `/data/adb/s23tweaks/dual5g/stock/` once and is never overwritten, a copy with a README goes to `Download/s23tweaks-modem-backup/`, and every write saves the file it replaces and is read back and compared, with the previous file written back on a mismatch. A marker comment records which codes the module added, so the original can be rebuilt even without a backup. Un-picking `dual5g`, removing the module, or `tweaks.sh dual5g-restore` puts the original back and restarts the modem; the service menu's MCFG HW & SW RELOAD is the fallback without the module. Verified on an SM-S918W with Airtel (data) and Jio: from the stock file, the apply backed it up, added 404, 405 and 406 and restarted the modem in about 23 s; afterwards Jio stayed on 5G SA as the standby SIM (11 of 12 samples over two minutes, versus never before) and both SIMs were on SA, and on VoNR, at the same time. `dual5g-restore` put back a byte-identical stock file, and a second apply wrote nothing.

The effect is Samsung's own (`WeatherWallpaperService` in the built-in live wallpaper app) and already runs on the S23, but the lock screen editor hid its **Weather** button. ## v1.4.0

- **Fix: Visual Cloud Core crashing with `galaxyai` on** (issue #19). `galaxyai` sets the AI version in `floating_feature.xml` to 20263, which the S24 Smart Suggestions needs for Now Brief. The S23's Visual Cloud Core reads the same key and, at 20261 or above, switches to the newer ("V2") interface of its C2PA (content credentials) library. The S23's library only has the older one, so Visual Cloud Core crashed with `UnsatisfiedLinkError: C2paLib.getVersion()`. The key can't be hidden from that one app, because Android parses `floating_feature.xml` once in zygote. `galaxyai` now puts a small adapter (`files/libC2paDps-shim.so`, source in `src/c2pashim`) over `/system/lib64/libC2paDps.camera.samsung.so`. It answers the four V2-only calls with the V1 ones, the same way Visual Cloud Core's own V1 path does, and forwards the other eight calls unchanged to the phone's original library, which is added beside it as `libC2paDps_s23.camera.samsung.so`. Nothing is downloaded and no S24 file is involved. If a firmware's library already has the V2 calls, it's left alone. The bug report's `galaxyai:` line shows `C2PA=shim` when it's in place. Verified on an SM-S918W with `galaxyai` on: opening a photo with content credentials in Gallery makes Visual Cloud Core load the V2 adapter through the shim (`C2paLib-Version: 1.0.0`) and read the manifest, with no crash. A direct test of all twelve calls returns exactly what the V1 calls return, both by path and by file descriptor.

## v1.3.8

- **Fix: HideKSU could remove every tweak from the whole phone** (`hideksu`, v1.3.6 and v1.3.7). Chrome's app zygote (`com.android.chrome_zygote_native`) and its sandboxed children run as app uids but in init's own mount namespace. The daemon treated them as user-installed apps and detached the module's mounts "in their namespace", which removed them for the whole system. Zygote then aborted every new app zygote and WebView process (`Failed open(/product/overlay/s23tweaks-aodbright.apk)`), so Chrome and apps that use a WebView crashed until a reboot. `hidemnt` now never detaches anything in init's namespace or its own. Seen and verified on an SM-S918B: aimed at init it detaches nothing; aimed at an app it detaches that app's mounts and init keeps them. **If you're on v1.3.6 or v1.3.7 with `hideksu`, update and reboot.**
- **HideKSU's automatic hiding works on One UI 7+** (`hideksu`). v1.3.6 read the system-app list from `/data/system/packages.xml` as text, but One UI 7+ stores it as binary XML (ABX). It found no packages, and its fail-safe turned automatic hiding off (only `hide-apps.txt` entries were hidden from). The apply now writes the list from the package manager (`pm list packages -s -u`) to `/data/adb/s23tweaks/hidemnt-system.txt` and the daemon reads that. Samsung's own apps installed from the Galaxy Store (`com.samsung.*`, `com.sec.*`: Voice Recorder, Samsung Health, language packs) now keep the mounts too, since they can read the tweaked feature files. Verified on an SM-S918B (One UI 9): 477 system packages listed, user apps hidden from, system apps keep the mounts.
- **AirDrop no longer fails along with Wi-Fi 7 on kernels where the two don't work together** (`airdrop` + `wifi7`, issue #21). On a custom ThinLTO kernel the S24 Wi-Fi driver came up fine for AirDrop alone, but not with `wifi7`'s MLO settings and S24 supplicant. Wi-Fi didn't come back, and AirDrop failed with "Wondertap provider not registered". Now, if Wi-Fi doesn't come up after the S24 driver loads and `wifi7` is on, `airdrop` removes the `wifi7` changes, reloads the driver and carries on without them. `wifi7` stays off until a reboot, which tries it again. Not tested on such a kernel (on a stock kernel this path never runs).

## v1.3.7

- **India stops Samsung's "Switch to <carrier>?" prompt** (`india`). With an Indian SIM whose carrier (e.g. Airtel) doesn't match the reported sales code, Samsung's CID Manager keeps popping a full-screen "Switch to Airtel?" dialog that offers to restart and re-flash the carrier customization (erasing carrier-app data), and it won't dismiss. Since `india` already forces the phone to report INS, that prompt is pure noise and fights the tweak. `india` now suppresses it: it disables `com.samsung.android.cidmanager` and denies that package's `SYSTEM_ALERT_WINDOW` appop. The appop is the real lever - the dialog is drawn by the `com.android.phone` process (shared uid 1001) under the CID Manager package, so disabling the package alone doesn't stop it. Both are reverted (package re-enabled, appop restored) when `india` is unpicked or the module is removed, tracked by a `$V/india_simprompt` marker. Verified on-device that denying the appop blocks the dialog (the system actively rejects the redraw) while leaving the rest of telephony untouched.

## v1.3.6

- **HideKSU hides the module's mounts from user-installed apps automatically** (`hideksu`). v1.3.5 hid the mounts only from apps you listed by hand in `hide-apps.txt`. The `files/hidemnt` daemon now decides by install origin: it hides the module's bind/overlay mounts from **every user-installed app** (banking apps, root detectors - the apps that have no reason to see them) and **keeps them for every preinstalled system/Samsung app** (Camera, Gallery, Settings, the Galaxy AI apps - the apps that actually consume the tweaks). The split reads each package's `FLAG_SYSTEM` from `/data/system/packages.xml`, which stays set even on a system app updated through the Galaxy Store, so updated consumers are kept too. You no longer have to list anything. `hide-apps.txt` becomes an optional override list: a plain `<package>` force-hides a system app, and a leading-dash `-<package>` force-keeps a user-installed one; the daemon reloads the file when it changes (no re-apply needed). This replaces the hand-maintained list because an enumerated consumer-keep-list is fragile - `floating_feature.xml` and `camera-feature.xml` are read by a broad, firmware-dependent set of Samsung apps, so a missed entry would silently break a tweak; keying on install origin can't, because no consumer is ever user-installed. Fails safe: if the package database can't be parsed, auto-hiding is disabled rather than risk hiding the mounts from the consumers. Not yet tested on a phone (built and syntax-checked; prior per-app hiding verified on SM-S918W against Native Detector 7.7.0).

## v1.3.5

- **HideKSU also hides the module's mounts from chosen apps** (`hideksu`). The module applies every tweak by bind/overlay-mounting into init's namespace, so the mounts are inherited by every app; a detector that scans `/proc/self/mountinfo` flags them as suspicious/inconsistent mounts (the files themselves are stock). HideKSU now ships `files/hidemnt` (from `src/hidemnt`), a small native daemon that watches for the apps listed in `/data/adb/s23tweaks/hide-apps.txt` via the kernel's process-event connector and, as each starts, enters only that app's mount namespace and detaches the module's mounts there. The system and every other app - including the Samsung apps the tweaks modify - keep the mounts, so nothing breaks. KernelSU's own "umount modules" is all-or-nothing (every non-root app), which would hide the mounts from those Samsung apps too and turn their tweaks off, which is why this is a per-app list. One package per line; edit and re-apply (or reboot) to reload. The list is seeded with the Native Detector test app so you can confirm it; add your own apps (banking, etc.). Verified on SM-S918W: Native Detector 7.7.0 went from flagging suspicious/inconsistent mounts to "The Environment is normal" (even with its experimental and custom-ROM detections on), while Samsung Camera and other apps kept their tweaks.

## v1.3.4

- **AirDrop on custom kernels built with ThinLTO** (`airdrop`, with the `allow-any-kernel` opt-in; issue #10). Such a kernel renames static symbols to `<name>.llvm.<hash>`, so the lookup for cnss2's `plat_env` failed ("plat_env not found in kallsyms") and the stock driver went back. Checked against the S918WVLU8GZIF `semwifi-service.jar` and `framework.jar`; not yet tested on a phone.

## v1.3.1

- **Horizontal lock levels small tilts, in the viewfinder too** (`camextras`; issue #8). v1.3.0's patch switched the recording stabilizer's levelling on, but the stabilizer clamps the correction to a per-sensor maximum from the S23's EIS tuning: 8°, since the S23 never shipped horizontal lock. So a 30° tilt still showed 22° and the picture seemed to turn with the phone. The module now also binds a copy of the stabilizer (`com.qti.eisv3.so`) whose 16 reads of that maximum become 30°, and does the same for the preview's separate stabilizer pair (EIS v2: a patched node that switches levelling on for Super steady = 2, and `com.qti.eisv2.so`), so the viewfinder levels as well. All are found by instructions; a part that doesn't match is skipped and the log says what that leaves. Limits, measured with the gyroscope against the video: the crop margin Super steady reserves (about 20%) caps the applied correction at roughly 20° on the ultrawide, the correction is smoothed so it trails quick moves, and Qualcomm's levelling snaps to the nearest 90° orientation. It is not the S26's 360° horizontal lock. On the main (1×) camera the margin is too small for it to show. Tested on S918WVLU8GZIF: at tilts up to about 15° the recorded horizon stays within a few degrees (it followed the phone at about 0.75× before), with no artifacts.
- **Opt-in for custom kernels** (`airdrop`, `wifi7`; issue #10). AirDrop and Wi-Fi 7 only ran on Samsung's own kernel for the supported GZIF builds. On one of those builds with another 5.15 android13 kernel, creating `/data/adb/s23tweaks/allow-any-kernel` now lets them try. The kernel still checks every symbol CRC (`CONFIG_MODVERSIONS`) and refuses the modules if one differs; the module then puts the stock Wi-Fi driver back, as it does for any failed load. Untested: I only have a stock kernel.

## v1.3.0

- **24 FPS in standard Video** (`cam24fps`, new; PR #11 by moesuito). Samsung Camera offers 24 fps only in Pro video. `cam24fps` adds `video` to the FHD, UHD and 8K 24 fps entries in `camera-feature.xml` (every other attribute kept) and binds a byte-patched copy of `SamsungCamera.apk` whose standard-Video allowlist (`te.f0.i`) gets UHD 24 and FHD 24 in two slots only Fold/Flip models use (8K 24 is already listed). QHD stays hidden. The patch is in `device/files/`, made by `tools/cam24patch.py`. The tweak goes by the stock `SamsungCamera.apk` itself, not the firmware name: it runs on any phone whose Camera APK has a known MD5, and checks the patched copy's MD5 too. So far that covers the 17.0.00.43 APKs of S918BXXUAGZIF and S918WVLU8GZIF, which differ in MD5 but take the same patch bytes (uninstall Camera updates first). Tested by the contributor on S918BXXUAGZIF (24 fps in FHD, UHD and 8K, with Log video, lens switching while recording) and on S918WVLU8GZIF: FHD, UHD and 8K clips record at 24/1 fps, and Log video, horizontal lock and photos still work with no Camera crashes.
- **AirDrop finds Apple devices again after Mosey updates itself** (`airdrop`). Google Play now pushes Mosey updates (1.0.927074190 → 1.0.980159239). The new Mosey checks for its native service (`IMoseyService`) once at boot and disables its own `ExternalSharingService` if it isn't there yet, which it never is, because the module starts `mosey_server` at the end of the apply. Play services then started its provider registry but found no provider, and Quick Share never listed iPhones or Macs (`isExternal=false`). The module now enables the service right after `mosey_server` registers. Verified on S918WVLU8GZIF after a full reboot: the service comes up enabled with no manual step, and the iPhone and Mac show up in Quick Share.
- **SmartSuggestions no longer crashes during the apply** (`galaxyai`, also `colortone`, `settingssearch`). The S24 APKs were bound about 30 s before the framework restart, ahead of the camera driver restarts. Any app process started in that window used the stock APK's parsed manifest with the new APK and crashed (`Failed to parse XML configuration from Canadian_dollar`): about 5 crashes per apply. The APKs are now bound just before the restart (a 1.2 s window); the library binds stay where they were. Verified on S918WVLU8GZIF: no crashes on a full boot apply, and all three tweaks still on.
- **HideKSU goes by the framework file, not the firmware name** (`hideksu`). It used to run only when the firmware was S918WVLU8GZIF. It now runs on any phone whose stock `/system/framework/services.jar` has the same MD5 as the one the patch was made from, and it checks the downloaded patched jar's MD5 before binding it. Its status also said "bound, waiting for a framework restart" forever: `system_server` runs the patched jar's code from memory, so the jar never shows in its memory map. It now reports on once `system_server` has restarted since the bind. Verified on S918WVLU8GZIF: the stock check passes, the status reads on after the restart, and CRED runs without crashing.

## v1.2.9

- **HideKSU: root-aware apps stop crashing** (`hideksu`). Apps like CRED kill themselves on launch when the KernelSU manager (`me.weishu.kernelsu`) is installed — their native anti-tamper enumerates installed packages through the package manager (CRED's `libSecureComponent.so` calls `getPackageInfo`), and a sandboxed app has no other way to see another app. `hideksu` binds a patched `services.jar` whose `AppsFilter` hides the manager from any third-party caller (appId ≥ 10000), except `df.root` (so DFRoot still loads root at boot) and the Samsung launcher (so the manager icon still shows). Nothing is injected into the apps, so their own `/proc/self/maps` scans stay clean — unlike an LSPosed/Zygisk module, which they can catch. The manager stays installed, so there's no more uninstall-before-you-use dance. Verified on S918WVLU8GZIF: with the KernelSU manager installed, CRED went from crashing every few seconds (NFC kept restarting its payment service) to running normally; the manager icon and root at boot both kept working. Needs firmware S918WVLU8GZIF (the patched `services.jar` is built for that exact build) and the KernelSU manager installed; applies on a framework restart.

## v1.2.8

- **Much less CPU with AirDrop on** (`airdrop`). The guard that reboots the phone cleanly if the Wi-Fi firmware crashes read the whole kernel log (about 260 KB) every second to look for the crash line. On an idle phone that was about a third of all CPU time: 2.86 s of CPU every 30 s, about 18 minutes of CPU in 3.4 hours. It now waits on `dmesg -W`, which blocks until the kernel logs something new: 0.02 s per 30 s. Measured on S918WVLU8GZIF. Phones keep the old guard until they reboot after updating the module.
- **Always On Display brightness follows the room light** (`display`). The AOD app builds its brightness from two framework tables (`config_autoBrightnessLevels_doze`, `config_autoBrightnessDisplayValuesNits_doze`) that the S23 ships empty, so every light reading logged "getBrightnessValues not matched!" and the AOD got 0 nits: it sat at its minimum, and the lock screen wallpaper on AOD showed bright for a few seconds and then dropped sharply. `display` now adds the S24 Ultra's two tables with a small static overlay (`files/aodbright.apk`, built from `src/aodbright`) layered onto `/product/overlay`, and restarts the framework. Samsung's package manager doesn't list the overlay ("not in allowed list"), but zygote loads it into every app's system resources, which is where the AOD app reads it. Tested on S918WVLU8GZIF: at 13 lux the AOD went from 0 to 14.5 nits. Not yet checked in bright light.

## v1.2.7

- **AirDrop loads after hours of uptime** (issue #7). Applying `airdrop` long after a reboot could fail with "Failed to register mac80211 hardware. Ret: -12": mac80211 needs one 128 KB block of contiguous memory for its transmit queues, and the kernel gives up on a block that large once memory is fragmented. `wonder.ko` now asks for a block that size first in a way that makes the kernel reclaim and compact until it gets one, and frees it just before registering. Tested on S918WVLU8GZIF at 2.6 hours uptime: the old `wonder.ko` failed 6 times in a row, the new one loaded first time. If it still fails, `tweaks.sh` compacts memory and retries twice. The AirDrop download is now `airdrop-S918WVLU8GZIF-2.tar.gz` (only `wonder.ko` changed).
- **Re-applying after a failed AirDrop load no longer swaps the Wi-Fi driver again.** When the S24 driver and firmware are already in and only `wonder` is missing, the apply loads just `wonder`. Before, each retry dropped Wi-Fi, stacked another firmware overlay and could fail with "firmware overlay".
- **Bug reports show whether Galaxy AI's secure storage is blocked** (issue #5). Now Brief's Personal Data Intelligence keeps its data in Samsung's Pass Storage, and Android refuses to create it ("Root detected", then a "creation failed" crash loop) when the system process can see an `su` file at one of a dozen classic paths (`/system/bin/su`, `/system/xbin/su`, `/data/local/su`, ...). With KernelSU, `/system/bin/su` shows up for apps granted root, so this happens when something running as the system user has root, or a module leaves an `su` file. The report now lists the `su` files the system process sees and the last Pass Storage log lines.

The code is found by its instructions, so other firmware with the same code works too; if it differs, the option still shows but won't level, and the log says so. Tested on S918WVLU8GZIF.
